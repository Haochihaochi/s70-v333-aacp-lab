# SDD-0001 — Repository SDD and completion guard

Status at authoring: ready for implementation. Scope: development tooling only.

This specification and its test cases are written before the guard implementation. The user's 2026-09-13 instruction authorizes this workflow change. It does not authorize vehicle installation or change the current wired-Android-Auto product scope.

## Requirements

| ID | Requirement |
|---|---|
| GOV-01 | Always-on repository guidance must require requirements, product behavior, technical design and test cases before implementation, including fixes and integration configuration changes. |
| GOV-02 | A repository-local skill must route knowledge extraction, implementation, and completion review to maintained S70 context and evidence. Preserve the existing requirements document as the canonical baseline. |
| GOV-03 | A read-only guard must reject changed implementation paths without a changed, ready SDD record that names those exact paths and real specification files. Documentation-only changes may proceed. |
| GOV-04 | Every declared requirement must map to a substantive test case. A completed change must have passing results, local evidence, and fingerprints matching the code that was tested. Missing, failed, blocked, or stale evidence must fail completion. |
| GOV-05 | Staged validation must inspect staged documents/code, never accept unstaged supporting files as committed evidence. CI must compare all changes against an explicit event base. Renames and deletions must not escape coverage. |
| GOV-06 | Malformed records, missing files, outside-repository paths, invalid bases, and ambiguous states must produce a nonzero diagnostic without executing record-supplied commands. |
| GOV-07 | Per-change completion must never certify the full vehicle system. System completion requires the existing G1–G5 hardware/recovery evidence and every mandatory system requirement. |

## Product behavior

Contributors follow `AGENTS.md` and `$s70-v333-sdd`. They maintain a readable change specification plus a JSON record under `docs/changes/`. Small tooling changes may keep requirements/product/technical sections in one document. Vehicle features must reference the system requirements and actual feature product/technical specifications; the generic architecture alone is insufficient.

The guard reports either structural SDD readiness or an actionable failure. `--complete` additionally requires completed records and fresh passing evidence. Its success message explicitly denies vehicle qualification. It does not launch tests, perform installation, or manufacture proof of prior review.

Review may be performed by the agent for work already authorized; do not require repeated owner approval for routine reversible development. Ask only for a material unresolved requirement or an action outside the authorized scope.

## Technical design

- Python standard library only; add `tools/sdd_guard.py` with a CLI and testable validation functions.
- A snapshot supplies changed paths and bytes from either the working tree relative to HEAD, the Git index relative to HEAD (`--staged`), or the working tree relative to an explicitly resolved commit (`--base REF`). Include untracked, non-ignored files in working-tree mode. Disable rename collapsing so both old/new names require coverage.
- Relevant paths are every changed non-Markdown file except SDD record/template JSON and `.gitignore`/`.gitattributes`. This covers source, tests, CI, build configuration, shell helpers, and submodule pointers without a language-extension allowlist.
- Only changed records can cover a new implementation diff; an unchanged historical record cannot silently approve future work. `--record PATH` supports deliberate preflight/completion validation of a specific record. Never validate old completion fingerprints against later unrelated changes by default.
- Record fields: `schema_version`, `id`, `status` (`draft`, `ready`, `complete`), `scope` (`tooling`, `integration`), `requirements`, `specifications` (`requirements`, `product`, `technical` file paths), `code_paths`, `review` (`by`, `basis`), `tests`, and `code_sha256` for completed records. Paths are literal repository-relative POSIX paths; no globs, absolute paths or parent traversal. Specifications/evidence are nonempty Markdown files.
- Each test has `id`, `requirements`, `level` (`host`, `emulator`, `reference`, `bench`, `vehicle`), `kind` (`automated`, `manual`), `procedure`, `expected`, `result` (`planned`, `pass`, `fail`, `blocked`, `not_run`), `test_file` for automated cases, and `evidence` for passing results. Actual test files must exist for completed automated cases. Completion requires at least one automated case for a code change.
- SHA-256 uses Git-style LF normalization for text portability across Windows/Linux. The fingerprint map includes every `code_paths` entry and every automated `test_file`, even if a test file is unchanged in the diff. Deleted paths use the explicit value `deleted`; submodule pointers hash `gitlink:<commit>` and must be clean for working-tree completion. Fingerprints bind record evidence to the inspected source snapshot, not to a proven APK build. The existing release-artifact gates still apply.
- `--complete` validates changed records or an explicit `--record` and rejects an empty selection. Default mode accepts `ready` work-in-progress and validates complete records strictly; it is not a merge-to-production approval.
- Wire the guard into `make guard`, the local pre-commit hook, and foundation CI. Fetch full history; use event base through an environment variable (not direct shell insertion). An initial push with an all-zero base uses the repository's documented pre-guard baseline commit. Manual CI uses the preceding commit only if it is at or after the governance baseline; otherwise use that baseline, so historical pre-guard changes do not spuriously fail. Invalid bases fail.
- Leave the existing requirements, receiver, profiler, installer, and uninstaller behavior unchanged. No vehicle build/install is part of this change.

## Test cases written before implementation

| Case | Requirement | Setup / action | Expected |
|---|---|---|---|
| G01 | GOV-03 | Change only Markdown | SDD check succeeds without an implementation record |
| G02 | GOV-03 | Add, modify, delete or rename code without a changed record | Check fails, naming uncovered paths |
| G03 | GOV-01, GOV-03 | Supply a ready changed record with requirements/product/technical files and test cases | Readiness succeeds; draft status or missing spec fails |
| G04 | GOV-04 | Omit a requirement's test mapping, expected outcome, or review | Check fails |
| G05 | GOV-04 | Declare completion with planned/failed/blocked results, absent evidence/test file or wrong digest | Completion fails |
| G06 | GOV-04 | Complete record has passing evidence, real automated test file, exact source digests and explicit deleted path | Completion succeeds for that change only |
| G07 | GOV-05 | Stage code/record but leave supporting spec/evidence unstaged | Staged check fails; working-tree check can succeed |
| G08 | GOV-05 | Keep a historical record unchanged, then change its code; compare a multi-commit branch to base | Old record cannot cover fresh changes; base comparison covers the whole diff |
| G09 | GOV-06 | Malformed JSON, wrong field types, missing/escaping paths, symlink, invalid base, empty completion selection | Diagnostic failure, no record-supplied command execution |
| G10 | GOV-04, GOV-05 | Equivalent CRLF/LF source; changed submodule pointer and dirty submodule | LF-normalized fingerprints agree; pointer handled; dirty completion rejected |
| G11 | GOV-01, GOV-02, GOV-07 | Review skill with a terse USB-fix request that omits specs, an assumption of CarPlay support, DHU presented as v333 proof, or a full-completion claim after host tests | Instructions preserve SDD, wired scope, hardware gates and honest completion wording; explicit user changes remain authoritative |

Pre-implementation refinement for G05/G09: explicitly test an automated test file changed after evidence capture even when absent from `code_paths`, and exercise CLI success/failure exit status. This closes a review-discovered source-freshness gap without changing vehicle scope.

CI acceptance cases: evaluate pull-request base selection, an all-zero first-push base and manual dispatch at the pre-guard baseline. Each must check the intended governance diff and pass with SDD-0001 evidence. An initial local manual-dispatch simulation failed because it selected an earlier historical commit; the manual-base rule above is the specified correction. Repeat these shell scenarios after changing the workflow.

Local hook acceptance: use a POSIX shell entrypoint and choose Python from `PYTHON`, then repository-local `sdd.python`, then `python3`. This allows the current Windows checkout to use its bundled interpreter without global configuration changes. Enable `core.hooksPath=.githooks` and set local `sdd.python` to the verified interpreter; run `git hook run pre-commit` and require both guards and the test suite to pass. On other clones bootstrap still requires an available Python 3 interpreter. The staged SDD test cases G07 remain the proof for rejecting unstaged supporting evidence.

## Validation record

Results belong in `docs/development/evidence/SDD-0001.md` after execution. The JSON record starts `ready` and is marked `complete` only once tests pass and fingerprints are captured. This record certifies development tooling only.
