# Change ID — title

Replace this template with a concrete design before implementation. Keep a matching JSON record under `docs/changes/`. This template is not readiness evidence.

## Requirements

State the authorized scope, requirement IDs and canonical sources, observation/inference, acceptance criteria, unknowns and exclusions. For integration, identify the exact target and current access/recovery gate.

## Product behavior

Describe owner/technician behavior before and after, normal journey, permissions, failure messages, factory return, and supported combinations. Do not promise unverified hardware behavior.

## Technical design

Describe changed modules/files, interfaces and data, state transitions, dependencies, permission boundary, factory-priority behavior, failure/recovery and migration, and how unknowns constrain implementation. Identify exact evidence needed for each external/hardware dependency.

## Test cases — before implementation

For each case record ID, mapped requirement IDs, environment, prerequisites, procedure/inputs, expected observable result, automation/manual approach and evidence to collect. Include success, denial/invalid input, interruption, recovery and regression cases appropriate to the change.

## Readiness review

Record reviewer, date, scope authorization, reviewed assumptions, unresolved gates and why the proposed code is ready. Readiness must precede implementation; approval is not a substitute for evidence.

## Execution and completion

Record actual commands/procedures, date, exact source/build/target/phone identity, results and evidence. Distinguish simulated from hardware results. Record completion only for the scope actually verified.
